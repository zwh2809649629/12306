# 查询任务生命周期与执行流程

> 最后更新：2026-09-25
>
> 本文描述 WebX 查询任务从创建、发布、查询、命中、下单到停止的完整生命周期。
> 当前任务对账为**手动单次执行**，不存在自动任务对账轮询。

## 1. 总体流程

以下使用纯文本阶段图，避免依赖 Mermaid 渲染器：


下单结果会进入以下三个出口：

```text

   │
   └─ 已确认排队但结果不明 ─► unknown ─► 停止任务并要求人工核对
```

## 2. 核心对象与职责

| 层级 | 对象或存储 | 职责 | 是否权威 |
|---|---|---|---|
| 持久层 | `runtime/webx.db` 的 `job` 表 | 保存任务配置、启停和完成状态 | 是 |
| 配置桥 | `ConfigSync` | 将 DB 中应运行的任务发布给原生引擎 | 否 |
| 引擎配置 | `Config.QUERY_JOBS` | 原生引擎当前应加载的任务配置 | 否 |
| 内存层 | `Query.jobs` | 当前进程内的 `Job` 实例集合 | 否 |
| 执行层 | Worker Thread | 执行 `Job.run()` 查询循环 | 否 |
| 目录缓存 | `job_train_catalog` | 保存任务车次及经停站，供详情页读取 | 否 |

任务真正健康运行需要同时满足：

```text
DB 要求运行
  AND Job 存在于 Query.jobs
  AND Job.is_alive = True
  AND Worker Thread 存活
```

只检查 `Job.is_alive` 不足以证明任务仍在查询。

## 3. 创建与发布阶段

### 3.1 创建任务

管理台提交任务后，服务端依次执行：

1. 校验日期、区间、车站、乘客、席别、时间段和启动方式。
2. 将任务写入 `webx.db.job`。
3. 调用 `ConfigSync.publish_jobs()`，让保存结果立即生效。
4. 在后台生成 `job_train_catalog` 任务目录缓存。

任务详情页只读取目录缓存，不会因为打开详情页而临时查询 12306。

### 3.2 判断是否可以发布

| DB 状态或条件 | 是否进入引擎 | 后续行为 |
|---|---:|---|
| 启用、未结束、已到启动时间 | 是 | 创建或复用 `Job` |
| 暂停 | 否 | 已存在的 `Job` 被停止 |
| 已成功或已结束 | 否 | 生命周期结束 |
| `start_at` 尚未到达 | 否 | 到点后由调度逻辑发布 |
| 已删除 | 否 | 删除任务及目录缓存 |

### 3.3 唯一身份

`sync.job_info_dict()` 会将 DB 主键写入 `webx_id`。该字段参与原生 `Job.id` 的计算，因此：

- 两个同名任务仍然拥有不同的 `Job.id`；
- 查询次数、命中、事件和结束原因可以落到正确任务；
- 修改站点模式、区间、日期或车次过滤等核心条件后，会重建对应 `Job` 实例。

## 4. Job 与 Worker 启动阶段

`Query.update_query_jobs()` 对发布后的任务执行刷新：

| 当前情况 | 处理方式 |
|---|---|
| 相同 `Job.id` 已存在且有效 | 复用现有实例 |
| DB 有任务但内存中不存在 | 创建新的 `Job` |
| 内存 Job 已不在发布配置中 | 调用 `destroy()` 停止 |
| 服务以零任务启动，之后新增任务 | 自动重新启动查询循环 |

每个 Worker 会记录以下生命周期信息：

```text
_webx_worker_thread       当前线程对象
_webx_worker_started_at   Worker 启动时间
_webx_worker_exited_at    Worker 退出时间；未退出时为 0
```

这些字段用于识别“Job 仍标记存活，但 Worker 已经死亡”的异常状态。

## 5. 单轮查询流程

一次查询轮次按以下顺序执行：

```text
[检查任务存活]
       │
       ▼
[获取可用账号与乘客]
       │
       ├─ 账号暂不可用 ─► 任务保持 active，等待账号恢复事件
       │
       ▼
[账号已就绪]
       │
       ▼
[按日期和区间请求 12306]
       │
       ▼
[解析余票响应]
       │
       ▼
[站点过滤]
       │
       ▼
[车次白名单/黑名单过滤]
       │
       ▼
[出发时间过滤]
       │
       ▼
[席别与余票状态过滤]
       │
       ├─ 无目标票 ─► 记录查询次数和耗时 ─► 等待下一轮
       │
       └─ 命中目标票 ─► 记录 hit_log ─► 进入下单链路
```

站点过滤使用票行的实际上下车站，避免 12306 同城扩展导致买错站：

- `exact`：只允许与输入站名完全一致的车站；
- `expand`：城市名可扩展到该城市官方归属的全部车站，具体站名仍只匹配自身。

账号暂时掉线或过期时，任务不会中止、暂停或写入结束状态，而是保留 `active`、`Job` 和 Worker，状态显示为 `blocked`。
普通查询在 `Job.query_by_date()` 的请求边界等待账号恢复事件；等待期间不调用原始查询函数，也不增加 `query_count`，不会产生假的查询结果。
账号恢复后由 `UserJob.user_did_load()` 发出账号级通知，自动唤醒该账号下等待中的任务并放行下一次真实查询。
若用户在等待期间暂停、删除任务或任务被销毁，`Job.destroy()` 会唤醒等待者，查询循环安静退出。
只有账号已就绪且确实找不到指定乘客时，才按不可恢复问题处理。

这里的“账号过期任务中止”不是本系统的设计：账号过期属于**暂时阻塞**，不是任务终态。
此前普通查询路径缺少这道账号就绪检查，曾导致页面显示 `blocked` 但仍继续请求；这是实现缺口，已由 WebX 查询闸门补齐。

## 6. 命中与下单阶段

余票命中后先写入 `hit_log`，然后按账号串行进入下单状态机：

```text
submitOrderRequest
        │
        ▼
      initDc
        │
        ▼
  checkOrderInfo
        │
        ▼
   getQueueCount
        │
        ▼
confirmSingleForQueue
        │
        ▼
 queryOrderWaitTime
```

最终结果及任务行为：

| 结果 | `order_log` 状态 | 任务行为 |
|---|---|---|
| 获得订单号 | `success` | 即时任务停止 |
| 服务端明确拒单或余票不足 | `failed` | 账号退避后继续查询 |
| 已确认排队但最终结果不明 | `unknown` | 停止任务，提示到 12306 官方订单页核对 |

“请求已受理”不代表生成订单。只有取得订单号才能记为成功。

明确拒单不会结束任务，否则一次排队失败就会让任务永久停止。

## 7. 暂停、恢复、删除和结束

### 7.1 暂停

```text
页面点击暂停
  → DB 状态先改为 paused
  → ConfigSync.publish_jobs()
  → 从 Config.QUERY_JOBS 移除
  → Query 刷新任务
  → Job.destroy()
  → Worker 在当前调用返回后退出
```

如果 Worker 正在长耗时下单或排队请求中，不会强行中断网络调用，而是在当前调用返回后检查 `is_alive=False` 并退出。

### 7.2 恢复

```text
页面点击启用
  → DB 状态改为 active
  → ConfigSync.publish_jobs()
  → 创建或恢复 Job
  → 启动 Worker
  → 继续查询
```

### 7.3 删除

删除任务后：

- 从 DB 删除任务；
- 删除对应 `job_train_catalog`；
- 重新发布任务配置；
- 引擎停止并摘除对应 `Job`。

### 7.4 生命周期结束条件

任务可能因为以下原因结束：

- 成功取得订单号；
- 用户暂停或删除任务；
- 即时任务完成；
- 乘客或配置存在不可恢复的问题；
- 排队已确认但订单状态不明，为防止重复下单而停止。

## 8. Worker 异常处理

`Job.run()` 顶层包装会捕获未处理异常：

1. 将完整 traceback 写入 `runtime/webx.log`；
2. 向任务详情写入 `error` 事件；
3. 设置 `_webx_worker_exited_at`；
4. 清空 `_webx_worker_thread`；
5. 重新抛出异常，让 Worker 真实退出。

这避免了以下假象：

```text
只查询一轮
+ 没有错误日志
+ Job.is_alive 仍为 True
+ 页面误以为任务还在运行
```

账号待恢复不属于 Worker 异常：Worker 可以保持存活并阻塞在账号就绪检查处，或在任务被停用时正常退出。
判断这两种情况时，应结合任务状态、账号就绪状态、`query_count` 和 Worker 线程状态，不能只看 `Job.is_alive`。

## 9. 手动对账

任务对账现在只在管理台点击“立即对账”时执行一次。

```text
[点击立即对账]
        │
        ▼
[读取 DB 中应运行任务]
        │
        ▼
[读取 Query.jobs]
        │
        ▼
[检查对应 Worker 是否存活]
        │
        ├─ 全部一致 ─► 返回任务数量和“未发现异常”
        │
        └─ 存在差异
              │
              ├─ 摘除 DB 已暂停/结束的残留 Job
              ├─ 摘除 Worker 已退出的失效 Job
              ├─ 调用 ConfigSync.publish_jobs()
              └─ 补载 DB 中应运行但引擎缺失的任务
```

一次手动对账处理三类问题：

| 问题 | 判断 | 修复动作 |
|---|---|---|
| 残留任务 | DB 不要求运行，但引擎 Job 仍存活 | 摘除并重新发布 |
| 缺失任务 | DB 要求运行，但没有对应 Job | 重新发布并补载 |
| 死亡 Worker | Job 标记存活，但 Worker 已退出 | 摘除旧 Job 并重建 |

执行结果写入日志：

```text
webx 手动对账：正常（DB 应运行 N，Job 存活 N，未发现异常）
```

或：

```text
webx 手动对账：已修复：摘除…；重载…；重启…
```

点击一次只执行一次，不会创建定时器，也不会在 30 秒后再次执行。

## 10. 30 秒后台守护的现有职责

30 秒后台线程仍然存在，但只负责：

1. 将全局查询次数差值累计到 `daily_query`；
2. 清理 `User.users` 中已经死亡的账号对象。

它不会检查、重启或修改查询任务，也不会自动执行任务对账。

## 11. 生命周期状态速查

| 阶段 | DB | Job | Worker | 含义 |
|---|---|---|---|---|
| 等待定时启动 | active，未来 `start_at` | 不存在 | 不存在 | 正常等待 |
| 正在查询 | active | 存活 | 存活 | 健康运行 |
| 账号待恢复 | active | 存活 | 存活或等待 | 状态为 `blocked`；暂停 12306 请求和查询计数，恢复后继续 |
| Worker 异常退出 | active | 可能仍显示存活 | 已退出 | 需要查看错误或手动对账 |
| 已暂停 | paused | 应不存在或正在退出 | 应退出 | 不再查询 |
| 下单明确失败 | active | 存活 | 存活 | 退避后继续查询 |
| 下单成功 | success/finished | 退出 | 退出 | 生命周期完成 |
| 订单结果不明 | finished/unknown | 退出 | 退出 | 人工核对，防止重复下单 |
| 已删除 | 无记录 | 不存在 | 不存在 | 生命周期终止 |

## 12. 排障顺序

任务看似运行但没有继续查询时，按以下顺序检查：

1. 确认 8600 端口只有一个服务实例。
2. 查看 `runtime/webx.log` 尾部是否有 Worker traceback。
3. 查询 DB，确认任务是否为 active、未结束且已到启动时间。
4. 检查 `Query.jobs` 是否存在对应 `Job.id`。
5. 检查 `Job.is_alive` 和 `_webx_worker_thread.is_alive()`。
6. 查看账号是否就绪、指定乘客是否存在。
7. 必要时在设置页点击一次“立即对账”。
8. 对账仍无法恢复时，根据 `error` 任务事件和完整 traceback 定位根因。

不要只根据页面状态或 `Job.is_alive` 单独判断任务是否真的在查询。
